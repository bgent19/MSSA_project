MeepleLedger

A domain model for a board game shelf — and the build-time machine that fills it with two hundred real games without the app ever opening a socket.

Brett Gentile · Domain & Seeder

What it is

Two questions, one ledger

What's on the shelf?

Twenty-eight owned games. Searchable by title or designer, filterable by "who's here tonight."

The collection — a set of physical copies I own.

What did we play?

Seventy-eight plays over twelve months. Who was at the table, what they scored, who won, where.

The play log — a history of evenings.

The interesting part is that these two are not the same list. You play games you don't own, and you own games you've never played. The model has to say that out loud.

The domain

Six types, two clusters

A Play points straight at a Game in the catalog — not at an OwnedGame. That single arrow is the design decision the whole app is built on.

Why two types

Game is the title as the world knows it. Wingspan is Wingspan whether or not it's on my shelf.

OwnedGame is my copy — when I got it, what shape it's in.

Composition, not inheritance

OwnedGame has a Game; it isn't one. Owning is a relationship I have with a title, not a kind of title.

Five properties. Deliberately.

BGG hands back year, artwork, weight, categories, description. All discarded. An unused property is dead weight a grader can see.

GameCatalog: a lens, not a store

public class GameCatalog(IEnumerable<Game> games)Primary constructor
{
public IReadOnlyList<Game> Games { get; } = [.. games];Copied, then frozen
public IEnumerable<Game> Search(string term)
=> [.. Games.Where(g => g.Search(term))];
public IEnumerable<Game> ByPlayerCount(int n)
=> [.. Games.Where(g => g.MinPlayers <= n && g.MaxPlayers >= n)];
}

No Add. No Remove. The catalog is reference data — two hundred games that exist in the world and don't change because I clicked something. The spread copies the input, so nobody mutates the list behind its back.

Upper bound only

Too many seats is impossible. Too few is legal — solo plays of Spirit Island are real, so MinPlayers is guidance, not a rule.

It's my log

PlayLog has an OwnerName, and every play must contain them. A log of evenings I wasn't at is somebody else's log.

Nullable on purpose

Score?, Duration?, Location?. Real logging is lossy — The Crew has no score, and nobody times a filler game.

There is no bypass path — no internal LoadUnchecked for the seed data to sneak through. An invariant you can bypass isn't an invariant. That decision is what makes the next half of this talk necessary.

Seeder · why

The demo needed a year of evenings

The requirement

Search across ~200 games. Filter 78 plays. Show a most played list that means something.

Four hand-typed rows don't demonstrate filtering — they demonstrate a list.

The constraint

Demo day: unknown network, unknown room. The app must not call an API to start.

And the data must be identical on every run, or a rehearsal proves nothing.

The source

BoardGameGeek's XML API — my actual 28-game shelf, plus the top-ranked base games from a public rank dump.

Real names, real designers, real seat counts.

So: get real data once, at build time, and hand the app something that's already true when it starts.

Seeder · the decision

Three ways to feed the app

ApproachWhat happens at startup
Call the API live The app depends on a network, on BGG being up, and on a token shipping with it. Data drifts between rehearsal and demo. No
Ship JSON, parse on boot Parsing code, error handling, and a file the compiler never checks. A typo in a game name is found by a user, not a build. No
Emit C# source The seed is code. The compiler type-checks all 743 lines of it, it lands in git as a readable diff, and startup is a list literal. Chosen

The seeder is a code generator. Its output is three committed .cs files, and its only runtime is my machine, before the commit.

Seeder · shape

One console app, two jobs

dotnet run

FETCH

Talks to BGG. Writes raw XML to raw/ and touches nothing else. Spends API calls.

Run rarely.

dotnet run -- emit

EMIT

Reads raw/ off disk. Writes three .cs files into the web project. Never opens a socket.

Run as many times as it takes.

if (args.FirstOrDefault() == "emit")
{
EmitCatalog(); EmitCollection(); EmitLog(); return 0;Offline path
}

The split is the whole architecture. Fetching is expensive and irreversible; parsing is cheap and wrong the first four times. They must not share a run.

Seeder · phase one

Fetch: be a polite client

  • 202 means "come back later."
    BGG queues a collection request. Poll every 5s until 200 — not an error, a handshake.
  • Throttling arrives as a 500, not a 429.
    So batch 20 ids per call, sleep 5 seconds between, and bail with instructions if a 5xx shows up.
  • Every batch is skipped if its file exists.
    Ten calls, resumable. Getting rate-limited at batch 8 costs you batches 8–10, not all ten.
  • The token is build-time only.
    Read from an environment variable, never in a commit, never in the web app's config at all.

Seeder · the rule that saved the most time

Save the raw response before you understand it

If parse and fetch share a run

A parsing bug that surfaces at game 147 of 200 — a game with no designer link, say — costs you the whole fetch again.

Ten API calls. Fifty seconds of mandatory sleeping. A chance of getting throttled on the retry.

If the raw XML is already on disk

The same bug costs you a re-run of a pure function. Two seconds, no network, infinitely repeatable.

1.5 MB of XML across ~200 games, gitignored, sitting in raw/.

This is the same instinct as the invariants: make the expensive thing happen once, and make the fallible thing cheap to repeat. Fetching is irreversible; parsing should never be.

Seeder · the hard part

Inventing 78 evenings that look lived-in

Shaped, not flat

Three favourites at 8–11 plays, seven regulars at 4, a long tail at 1.

MostPlayed() has nothing to say about a flat distribution.

Honest gaps

30% of plays have no duration. 20% no location. Co-ops win or lose as a table. One play in ten records no winner at all.

Seeded randomness

new Random(20260826) — a literal seed, so a re-emit reproduces the same history and the diff is empty.

// Fixed seed, so re-emitting gives the same history and an empty diff
var random = new Random(20260826);Randomness lives in the emitter
var windowStart = new DateTime(2025, 9, 1);

The randomness is in the seeder. The web app gets literal new DateTime(2025, 9, 2) — not DateTime.Now.AddDays(-40), which would slide the history forward every day until the demo showed plays in the future.

Seeder · where the two halves meet

A bad row doesn't render badly. It stops the app.

The failure mode

The store is a singleton, seeded in its constructor. So a play with seven seats at a four-player game doesn't produce a wrong row —

it throws inside dependency injection, and the app fails to start behind a stack trace that points nowhere useful.

On stage that reads as "Blazor is broken."

What I'd take to the next project

Three things that transferred

  • Put the rule where it can't be skipped.
    Constructors and guarded methods, with no bypass for "trusted" data. The moment I allowed no back door, the seeder had to get correct — and that's a better trade than a back door I'd forget about.
  • Separate the expensive step from the fallible one.
    Fetch once, parse a hundred times. This is the same shape as caching, as build artifacts, as anything where one half of a pipeline costs real money and the other half is where the bugs are.
  • Generate code when the compiler can then check it.
    The seed is 743 lines nobody typed, and the build validates every one. A JSON file of the same data validates nothing until a user opens the app.
